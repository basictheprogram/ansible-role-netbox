# ansible-role-netbox

Deploys NetBox as a Docker Compose stack on Ubuntu hosts. This role is the source of truth
for NetBox configuration across all sites. It is location-agnostic and network-agnostic —
all site-specific values live in inventory, group_vars, and host_vars, never in the role itself.

# Current workflow (pre-Ansible, replaced by this role)

* A Ubuntu VM is spun up (Ubuntu 24.04 as of April 2026)
* VM may be on VMware or Proxmox; future deployments will be Proxmox only
* openssh, git, and docker are installed into the VM
* SSH into the VM, git clone the netbox-docker project (https://github.com/netbox-community/netbox-docker)
* Manually tweak env/netbox.env, docker-compose.override.yml, and run docker compose up

This process is not DRY, does not scale, and causes state drift between sites.

# Requirements

* Ansible playbooks must work with Ubuntu 24.04 and Ubuntu 26.04
* No orphaned git-cloned repositories of netbox-docker on each Docker host
* No manual file tweaking — Ansible owns all configuration
* All plays must be idempotent
* Keep deployments DRY; eliminate state drift between sites
* All Docker images pinned to prevent surprise upgrades
* Controlled rollouts per region for upgrades
* Each site is fully isolated — no shared state between regions

# Soft dependencies

This role does not install Docker. Docker (with the Compose plugin) must be present and
running on the target host before this role is applied. This is treated as a soft dependency:
the role performs a preflight assertion that Docker is installed and the daemon is active,
and fails fast with a clear message if it is not.

Docker installation is the responsibility of a separate play or role run prior to this one.

# Upstream compatibility constraint

* This deployment MUST follow upstream netbox-docker conventions exactly
* The upstream docker-compose.yml is treated as the reference implementation
* Any deviation from upstream volume paths, service definitions, or defaults must be
  explicitly justified in this document
* Where upstream defines database or Redis volume paths, those paths are authoritative

## Known deviations from upstream docker-compose.yml

### netbox depends_on uses condition: service_healthy

Upstream uses the shorthand `depends_on: [postgres, redis, redis-cache]`, which
defaults to `condition: service_started`. This causes a startup race condition on
fresh deployments: Docker starts netbox as soon as postgres launches, but postgres
needs additional time to initialize a new database cluster. The netbox entrypoint's
30-second DB wait loop is not long enough to cover a cold postgres initialization.

Our copy uses `condition: service_healthy` for all three dependencies, ensuring
Docker Compose waits for each service to pass its healthcheck before starting
netbox. When reviewing upstream diffs during upgrades, preserve this change.

### netbox healthcheck start_period extended to 300s

Upstream uses `start_period: 90s`. On a fresh database, NetBox applies the full
migration history before starting the web server. This routinely exceeds 90
seconds, causing the healthcheck to declare the container unhealthy before nginx
is listening. `netbox-worker` depends on `netbox:service_healthy`, so the entire
stack aborts. 300s gives migrations a safe runway on first deployment without
affecting steady-state restarts (where migrations are a no-op and startup is fast).

### restart: unless-stopped on all services

Upstream does not set a restart policy on any service. Without one, Docker leaves
all containers in the exited state after a host reboot and never brings them back.
All five services (netbox, netbox-worker, postgres, redis, redis-cache) carry
`restart: unless-stopped` so the stack recovers automatically after a host reboot
or power event. `unless-stopped` is preferred over `always` so that containers
intentionally stopped by an operator (e.g. `docker compose down`) stay down until
explicitly started again. When reviewing upstream diffs during upgrades, preserve
this addition — upstream does not set a restart policy.

# Configuration model

* docker-compose.yml is treated as the upstream source of truth and is shipped as a
  static file inside this role (files/docker-compose.yml)
* All environment configuration is generated by Ansible from templates and variables
* docker-compose.override.yml is not used

# Deployment model (Option A — rendered configuration)

* The upstream netbox-docker repository is a reference implementation only
* No git clone of netbox-docker occurs on target hosts
* The docker-compose.yml is maintained in this role's files/ directory as a static copy
  of upstream and updated manually when upstream releases a new version
* All four env files are generated by Ansible templates at deploy time
* Rationale:
  * Eliminates orphaned repositories on hosts
  * Ensures structurally identical deployments across all sites
  * Keeps per-site variation entirely in variables, not in files
  * Reduces upgrade complexity — one role update applies everywhere

## Upgrade process

Upstream releases are tracked manually by watching:
https://github.com/netbox-community/netbox-docker/releases

When a new release is relevant:
1. Review the upstream diff for docker-compose.yml structural changes
2. Update files/docker-compose.yml in this role if needed
3. Bump netbox_version in group_vars
4. Test against one site, then roll out to remaining sites

# Deploy directory layout on host

All files are deployed under a single root directory (default: /opt/netbox).

```
/opt/netbox/
├── docker-compose.yml
├── env/
│   ├── netbox.env
│   ├── postgres.env
│   ├── redis.env
│   └── redis-cache.env
└── configuration/              # mounted read-only into netbox container
```

The deploy root is controlled by the `netbox_deploy_dir` variable (see Variable hierarchy).

# Variable hierarchy

Variables are split across three layers. The role itself never contains site-specific values.

| Layer | Location | Contains |
|---|---|---|
| Role defaults | defaults/main.yml | Safe defaults: version, deploy dir, feature flags |
| Role constants | vars/main.yml | Internal paths derived from netbox_deploy_dir |
| Group config | group_vars/netbox.yml | Shared non-secret config across all netbox hosts |
| Host identity | host_vars/<hostname>.yml | Per-site values: region, fqdn, email relay, etc. |
| Secrets | Ansible Vault (group or host) | Passwords, keys, tokens |

Site-specific values (hostnames, IP addresses, domain names, email relays) must never
appear in the role. They belong exclusively in host_vars or group_vars.

# Secrets management

Secrets are stored in Ansible Vault and templated into env files at deploy time.
No secrets are stored in Git in plaintext.

Secrets managed by this role:
* Database password (netbox_db_password)
* Redis password (netbox_redis_password)
* Redis cache password (netbox_redis_cache_password)
* NetBox SECRET_KEY (netbox_secret_key)
* NetBox API_TOKEN_PEPPER (netbox_api_token_pepper)

# Database strategy

* Each site has its own local Postgres container
* Database is not HA
* Backups:
  * Veeam with Postgres-aware handling
  * Backups stored on Veeam server, external USB disk, and remote Synology NAS
  * cron runs pg_dump; dumps stored locally, on external USB disk, and remote Synology NAS

# Redis strategy

* Redis (Valkey) runs as a local container on each site
* Two instances: one for general use, one for caching
* No shared Redis between sites

# Persistent storage

* All persistent storage is local disk via named Docker volumes
* Volume names follow upstream netbox-docker conventions exactly
* Backups handled externally (see Database strategy)

# Image strategy

* Use the upstream netbox Docker image from docker.io/netboxcommunity/netbox
* All image tags are pinned — no `latest` tags
* Image versions are controlled via the `netbox_version` variable
* Postgres and Valkey image tags are also pinned via variables

# NetBox networking within Docker

* NetBox containers are not exposed directly to the host network
* TLS termination and external access are handled by ansible-role-traefik
* This role handles the Traefik integration labels as a compose merge layer

## Traefik integration

The upstream `docker-compose.yml` is kept clean of site-specific values.
Traefik labels and network membership are added via a separate templated
file (`docker-compose.overlay.yml.j2`) that is merged at runtime:

```
docker compose -f docker-compose.yml -f docker-compose.overlay.yml up
```

This file is not a deprecated override — it is Ansible-managed and rendered
from `templates/docker-compose.overlay.yml.j2` using `netbox_fqdn` from
`host_vars`. The `docker-compose.override.yml` pattern (hand-edited per host)
remains deprecated and must not be used.

The netbox service joins two networks:
* `default` — the project-scoped default network created by docker-compose.yml,
  shared with postgres, redis, and redis-cache. Must be explicitly retained in
  the overlay; Docker Compose merge replaces rather than appends network lists,
  so omitting `default` here would isolate netbox from its dependencies.
* `traefik_proxy` — external network created by ansible-role-traefik; gives
  Traefik visibility to route traffic to port 8080.

Traefik routes `Host(netbox_fqdn)` → port 8080 with the `security-headers`
middleware and TLS via the `websecure` entrypoint.

# Reference: upstream docker-compose.yml

This is the upstream file shipped in files/docker-compose.yml.
Source: https://github.com/netbox-community/netbox-docker

```yaml
services:
  netbox: &netbox
    image: docker.io/netboxcommunity/netbox:${VERSION-v4.5-4.0.2}
    restart: unless-stopped
    depends_on:
      - postgres
      - redis
      - redis-cache
    env_file: env/netbox.env
    user: "netbox:root"
    healthcheck:
      test: curl -f http://localhost:8080/login/ || exit 1
      start_period: 90s
      timeout: 3s
      interval: 15s
    volumes:
      - ./configuration:/etc/netbox/config:z,ro
      - netbox-media-files:/opt/netbox/netbox/media:rw
      - netbox-reports-files:/opt/netbox/netbox/reports:rw
      - netbox-scripts-files:/opt/netbox/netbox/scripts:rw
  netbox-worker:
    <<: *netbox
    depends_on:
      netbox:
        condition: service_healthy
    command:
      - /opt/netbox/venv/bin/python
      - /opt/netbox/netbox/manage.py
      - rqworker
    healthcheck:
      test: ps -aux | grep -v grep | grep -q rqworker || exit 1
      start_period: 20s
      timeout: 3s
      interval: 15s

  postgres:
    image: docker.io/postgres:18-alpine
    restart: unless-stopped
    healthcheck:
      test: pg_isready -q -t 2 -d $$POSTGRES_DB -U $$POSTGRES_USER
      start_period: 20s
      timeout: 30s
      interval: 10s
      retries: 5
    env_file: env/postgres.env
    volumes:
      - netbox-postgres:/var/lib/postgresql

  redis:
    image: docker.io/valkey/valkey:9.0-alpine
    restart: unless-stopped
    command:
      - sh
      - -c
      - valkey-server --appendonly yes --requirepass $$REDIS_PASSWORD
    healthcheck: &redis-healthcheck
      test: '[ $$(valkey-cli --pass "$${REDIS_PASSWORD}" ping) = ''PONG'' ]'
      start_period: 5s
      timeout: 3s
      interval: 1s
      retries: 5
    env_file: env/redis.env
    volumes:
      - netbox-redis-data:/data

  redis-cache:
    image: docker.io/valkey/valkey:9.0-alpine
    restart: unless-stopped
    command:
      - sh
      - -c
      - valkey-server --requirepass $$REDIS_PASSWORD
    healthcheck: *redis-healthcheck
    env_file: env/redis-cache.env
    volumes:
      - netbox-redis-cache-data:/data

volumes:
  netbox-media-files:
    driver: local
  netbox-postgres:
    driver: local
  netbox-redis-cache-data:
    driver: local
  netbox-redis-data:
    driver: local
  netbox-reports-files:
    driver: local
  netbox-scripts-files:
    driver: local
```
